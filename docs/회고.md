# 회고 — Threads 예약 발행 MVP

## 무엇을 잘랐나

가장 아까웠던 건 **답글 자동응대**였다. 공식 API에 `pending_replies` / `manage_reply`가 있어서
할 수 있다는 걸 확인까지 해 뒀는데 뺐다. 넣으면 안전 필터·레이트리밋·중복 응대 방지가 줄줄이
따라오고, 그러면 **한 흐름도 끝까지 못 돌렸을 것**이다.

이미지 발행도 잘랐다. 이건 덜 아까웠는데, 자르고 나서야 이유가 선명해졌다 —
착수를 막던 세 가지(권한 체계 미착수, 미디어 업로드 스펙 미검증, 자산 테이블 부재)가
**텍스트 전용으로 자르니 한꺼번에 비껴갔다.**

**자르는 게 미루는 게 아니라 길을 여는 것**일 때가 있다.

## 오늘의 진짜 산 — 중복 발행

멱등키를 만드는 것까지는 쉬웠다. 어려운 건 **어디서 뚫리는지 아는 것**이었다.

```
검사와 변경 사이에 await 를 두지 않는다.
한 줄이라도 끼면 그 틈으로 중복이 들어온다.
```

"먼저 조회하고 없으면 삽입"이 가장 자연스러운 코드인데, 그게 바로 뚫리는 자리다.
그래서 주석으로 구간을 명시해 뒀다. 다음에 이 코드를 만지는 사람이 무심코 `await`를 끼우지 않게.

그리고 마지막에 하나 더 배웠다. **멱등성을 아무리 잘 짜도 "어디까지 이미 일어났는가"를 놓치면 뚫린다.**

본문=후킹 / 첫 댓글=본론 패턴을 붙이면서 발견했다. 첫 댓글이 실패했을 때 잡 전체를 실패로
되돌리면, 재시도할 때 **본문이 두 번 올라간다.** 본문은 이미 성공했기 때문이다.
그래서 본문 발행 지점을 경계로 나눴다.

## 어디서 막혔나 — 세 번 틀렸다

1. 참고할 문서를 잘못 짚었다 — 실제 기준 문서는 다른 곳에 있었고, ID 체계부터 달랐다
2. 다운받아 둔 프로그램을 폴더 구조만 보고 지목했다 — 영상을 확인하니 다른 프로그램이었다
3. "이 코드가 최고 자산"이라고 분석해 놓고, 정작 클라이언트를 새로 짰다

**셋 다 확인하지 않고 단정했을 때 틀렸다.**

특히 3번이 뼈아팠다. 이미 돌아가는 검증된 코드를 두고 새로 짜는 건 흔한 실수인데,
내가 쓴 분석 리포트에 답이 적혀 있었는데도 그랬다.

## 예상 못 했던 것

**작업의 절반이 "만드는 일"이 아니라 "이미 정해 둔 걸 찾는 일"이었다.**
공식 API만 쓴다는 결론도, 발행 흐름 설계도, 훅 라이브러리도 이미 문서에 있었다.
진행률만 0%였을 뿐이다.

그런데 **써 둔 걸 지키는 건 또 다른 일**이었다.
`.gitignore`에 *"커밋되면 세션 쿠키까지 올라간다"*고 적어 놓고도 그 폴더를 저장소로 만들 뻔했다.
**적어 두는 것과 지키는 것 사이에 틈이 있다.**

그래서 규칙을 문서가 아니라 **코드**로 옮겼다.
훅 중복·직접 판매어·CTA 누락은 이제 검증 게이트가 거절한다.

## 잔버그에서 배운 것

- **테스트가 시계에 따라 깨질 뻔했다.** 예약 픽스처를 가까운 미래 날짜로 뒀는데, 실제 시각이
  그 시점을 지나면 "과거 예약"으로 거절돼 실패한다. **오늘 통과했다고 내일 통과하는 게 아니다.**
- **타입체크가 테스트 파일에서 걸렸다.** `number | null`을 비교에 그대로 넘겼는데
  테스트는 통과하고 `tsc`가 잡았다. 그래서 둘 다 돌려야 한다.
- **`demo` 스크립트가 실행 불가능했다.** Node 22.6+ 전용 플래그를 쓰면서 `engines`에는
  20.6을 적어 뒀다. **써 놓고 한 번도 안 돌려 본 것이다.**
